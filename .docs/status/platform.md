- `analytics-embeddings` implemented (stage 3, branch `analytics/analytics-embeddings`): embeddings client for local `bge-m3` (`EMBED_*`, Redis cache, breaker, `model.embedder`, ADR 0313); dictionary topic gate before the modules (`off_topic`, `iw:stats:gate`, `firm_own` never gated); MinHash near-dup groups in Redis with one `finding.high_risk` per group and module and a summary sentence naming the original (ADR 0314); own numpy MinHash instead of datasketch (which loads scipy, about 115 MB). Gate similarity to centroids is a stretch item, not built. Infra ask for Kacper: issue #65 (`bge-m3` in `ollama-pull`, `OLLAMA_MAX_LOADED_MODELS=2`, `OLLAMA_KEEP_ALIVE`).
- `analytics-embedding-gate` (Damian's request, branch `analytics/analytics-embedding-gate`): the topic gate uses embeddings. A `third_party`/`unknown` document the dictionary drops (at least 40 characters) is embedded and passes when `max cos(on-topic centroid) − cos(off_topic centroid) ≥ GATE_EMBED_MIN_MARGIN` (0.03; on `analytics/eval/gate_check.jsonl` with `bge-m3`: P 1.0, R 1.0). Embeddings never re-judge a dictionary pass. With no embedder, the gate is dictionary-only. The centroids are built between messages. The path (`dictionary`/`embedding`/`dictionary_only_fallback`) is in the skip log and `iw:stats:gate`. `GATE_SIM_THRESHOLD` is replaced by `GATE_EMBED_MIN_MARGIN` and `GATE_EMBED_MIN_CHARS` (ADR 0314 amendment). Real stack run: 56 Telegram posts with no dictionary term took the embedding path, 34 rescued (about 31 of them trading posts), 22 dropped. In a scan burst on a loaded CPU, the breaker can hold the gate dictionary-only for a cooldown (follow-ups F6). `ollama-pull` is broken by the `OLLAMA_MODELS` clash (issue #149).
- `analytics-m2-text-rules` implemented (branch `analytics/analytics-m2-text-rules`): R10 language consistency (rules-only, additive `preprocessing.sentence_language`, main language from non-footer, non-legal blocks or body sentences) and R9 comprehensibility (LLM-first: rules give `uncertain` on long or jargon-heavy warnings, the LLM rates 1-5, `fail` only at 2 or lower with a verified quote, via the new `Rule.accept_llm_verdict` hook). Classes in `rules/m2_text.py`. Decided by Damian: a rules-only R9 `uncertain` is listed but not scored (catalogue flag `llm_only_uncertain`), so the M2 default stays 0.1.
- `analytics/compose-single-build` (fix, no OpenSpec change): only `analytics` builds `investwatch/analytics`; `analytics-eval` reuses the image like `api` does with `api-migrate`, so `docker compose up --build` no longer aborts on two parallel exports to one tag ("image ... already exists" with the containerd store). The build context is `../analytics`, so the `-f infra/compose.yaml -f api/compose.yaml -f analytics/compose.yaml` command in the file header builds too (before, `.` resolved to `infra/`).
- `analytics/fix-worker-test-130` (test-only fix, no OpenSpec change, issue #130): `test_real_redis_autoclaim_and_delivery_count` patched the removed `worker.analyze` and failed in CI's `Python services (3.12)` job. It now patches `analyze_document` through `monkeypatch`. Verified against a real Redis.
- `analytics/m2-p1-hostile-input-perf` (fix, no OpenSpec change): `main` was red after #93. The new M2 P1 rules doubled `analyze` CPU time on the hostile `claim-warning-pairs` input (1.98 → 4.0 CPU s, budget 3.0, `tests/test_redos.py`). The past-performance detector now runs once per document for R14/R12a/R12b; R11 blanks its exclusions once for both lists; R16 builds its exclusion list once; exclusion `sub`s are skipped when none occurs. Back to 1.95 CPU s. Rule outputs are byte-identical on the mocks, the gold set, hostile and 300 random documents.
- `analytics/eval-wait-healthcheck` (fix, no OpenSpec change): `docker compose up -d --wait` exits 0 again. Before, it exited 1 with "analytics-eval has no healthcheck configured" although every service was healthy or exited 0. `--wait` checks a service nobody depends on for "running or healthy", which a one-shot fails either way: with `healthcheck: disable: true` it is "no healthcheck configured", and with no healthcheck it is "exited (0)" once the run has finished. `analytics` now depends on `analytics-eval` with `service_completed_successfully` and `required: false`, so `--wait` checks completion, as for `api-migrate`. The worker still starts if the evaluation fails, and `--wait` then exits 1 with "didn't complete successfully". The image `HEALTHCHECK` stays in `analytics/Dockerfile` as the `document-stream-worker` spec requires.
- `analytics-stored-content-hash` (issue #31, Damian's decision): analytics no longer computes a `content_hash` (`preprocess()` had an NFKC one, used only as the LLM cache key); it uses the stored NFC value the scraper writes as is, also for the LLM cache key, and a document without one is not cached ([ADR 0105](../decisions/0105-content-hash-normalisation.md)). NFKC `normalize()` stays for matching, language guess and excerpts. Open: `contracts/mocks/generate_mocks.py` still lowercases before hashing (`content-hash-definition` follow-up 4, Damian's own decision).
- `api/compose-build-157` (fix, no OpenSpec change, issue #157): `api` and `api-migrate` each build `api/Dockerfile` under their own tag (`investwatch/api`, `investwatch/api-migrate`), so `docker compose up -d --build --no-deps api` rebuilds the API. Before, only `api-migrate` built, and a targeted rebuild kept the old image, which is how the demo stack missed PR #139. One shared tag built by both races on the image store (reproduced with Compose v2.40), and `build:` on `api` alone breaks `up api-migrate` without `api` (pull denied).
- `analytics-deepseek-default` (ADR 0318, Damian's decision, branch `analytics/analytics-deepseek-default`): the hosted default LLM is DeepSeek Flash (`deepseek-flash` at `https://api.deepseek.com`, limits 60 / 90 / 120000), and Gemma 4 on the Gemini API (ADR 0317) is a documented alternative.   - Not changed here: `.docs/presentation-analytics.md` and `.docs/hand-in.md` (another session), and the demo stack `iw-demo`, which keeps its Gemma cache.
