# iw-commit-cycle

Runs inside `/openspec-apply-change`. OpenSpec picks the tasks and ticks them; this skill defines what "done and committed" means. Per **task group** (the tasks that make one coherent commit):

1. **Test first.** The group's first task is a failing test. Name the production change that would turn it red, run it, and confirm it fails for the intended reason (not an import error). Parsers and fixtures: saved real responses under `tests/fixtures/`, never live network in unit tests. (`ecc:tdd-guide` may be used if installed; it is not required.)
2. **Implement** the minimum, run the test green, then the module's full suite, lint and type check. Keep the command and result; a run before the last edit does not count.
3. **Mutation check (required).** A test that cannot fail proves nothing. For every guard, validation, branch, boundary or parse rule the group adds or changes, list one mutation each (remove the guard, invert the condition, move a boundary by one, drop one conjunct of a compound condition), and for each: back up the file, apply the mutation with a script that asserts the old snippet exists (a no-op "mutant" is not a mutant), run only the scoped test, restore, and confirm `git diff` of that file is exactly what it was before the mutation (an interrupted run must never leave a mutant to be committed). A valid red is a non-zero exit with an output naming the expected assertion; "no tests found", an import error or a timeout is not. A surviving mutant means a missing test case: add it, then repeat. Write the result on the group's mutation-check task in `tasks.md` as `mutations: N tried, N caught` (the PR body copies those lines; `iw-pr-review` checks them). Exempt only: docs-only, pure-rename, and config-only groups, where config means values with no logic (env, compose, yaml settings); a hook, validator, parser or rule is code and is not exempt. A group that changes only tests or fixtures is not exempt when it pins a guard: mutate that guard. Say so in the line (`mutations: n/a, <reason>`). Optional accelerators if installed: `mutmut` (Python), StrykerJS (JS).
4. **Validate**: `openspec validate <slug> --strict`, and `node .claude/skills/iw-docs-update/scripts/docs-check.mjs` if you touched docs or added a service directory.
5. **Stage, then commit, as two separate tool calls** (`git add <paths>`, then `git commit`). The `git-guard` hook reads the staged diff when the command starts, so a chained `git add ... && git commit` is denied. Conventional Commit, terse subject, no `Co-Authored-By`. If the hook denies a commit, fix the cause; don't reach for an escape flag, and if one is genuinely needed ask the human and report its use in the PR body.
6. **Review** once per task group, and before every push, whichever comes first (not after every single commit). Dispatch the `iw-reviewer` agent (in `.claude/agents/`; `/code-review` is the fallback) with: the worktree path, the pinned range `BASE=$(git merge-base HEAD origin/main)` to the HEAD sha, the change name, and `focus: security` for contract, credential, proxy, outbound-request or LLM-prompt changes. It reads and reports; it does not edit.
7. **Verify every finding** against the code before acting. Fix real ones in follow-up commits (never amend a pushed commit); reject false ones with a one-line evidence note. After 3 rounds on one group, stop and ask the human.
8. **Triage out-of-scope findings** and the reviewer's "declined to judge" list into the change's `follow-ups.md` (create it if absent), one row each with one disposition: `fix-here`, `new-item` (GitHub issue), `wont-fix` (reason) or `docs`.

Each review is a fresh agent; nothing is carried across sessions.
