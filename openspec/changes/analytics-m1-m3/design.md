# Design

## Context

`analytics/` on `main` has a pure `analyze(doc, *, registry, catalogue, now, new_id)` that routes `firm_own` documents to M2 (rules R1-R3) and drops everything else with `module_not_implemented` (`modules/router.py`, skeleton design decision 5). The unmerged `analytics-worker` wraps it with the Redis stream consumer, the Postgres upsert on `(document_id, module)` and the `iw:events` publisher, and it adds `AdvertiserRef` to `Finding` (worker commit `b35348b`). Its publisher already applies the per-module thresholds M1 0.6 / M3 0.7 (ADR 0305), so M1/M3 findings flow end to end once the pipeline returns them.

The signals, the score shape and the M3 hard gate come from `.docs/analytics-plan.md` §4 and §6. The contract is `Finding` v1 (`.docs/integration-plan.md` §4): `rule_id` accepts `S1.x`/`S3.x`, and `advertiser` has `name`, `handle`, `profile_url`, `website`, `in_registry` and `on_warning_list`. The mocks in `contracts/mocks/` (generated by `generate_mocks.py`) show the intended M1/M3 output for six documents. They are illustrative, not a gold set: some of their evidence is not in the document (`Blog finansowy`), and some results come from an LLM.

The sibling stage-2 change `analytics-llm-p0` builds the LLM client (OpenAI-compatible, ADR 0304), the prompt, the Redis cache and the M2 P0 rules. Its design (§1 "the engine defers, the judge decides", §2 "the seam for `analytics-m1-m3`") defines the seam, and this change follows it (decision 6) instead of defining a second one.

## Goals / Non-Goals

**Goals:**
- Rules-only M1 and M3 that produce contract-valid, explainable findings for the six mock documents, without an LLM.
- M1 and M3 on the shared rule engine (YAML catalogues, evidence safety net), so the LLM seam of `analytics-llm-p0` applies to them without new merge code.
- The LLM fills S1.4 (adds only), S1.5, S3.3 and S3.4 later, with a defined rules-only degradation.
- Only small, additive edits to `rules/engine.py`, and none to `rules/m2.py` or `m2_rules.yaml`, which `analytics-llm-p0` changes.

**Non-Goals:**
- The LLM client, prompt text, cache and response parsing (`analytics-llm-p0`).
- The topic gate, embeddings, near-duplicates (plan §2 steps 1-2).
- The KNF public warnings list (S3.7), the real KNF loader, inflected firm names.
- Weight calibration on a gold set (plan §8). The weights here are hand-tuned starting values.
- Running several modules on one document (plan §2 says "possibly several"); see Open Questions.

## Decisions

1. **Routing by registry result.** `firm_own` → M2, unchanged (an unmatched own page still goes to M2, where R1 fails). `third_party`/`unknown` with a registry match → M1. Without a match → M3. An M3 document whose advisory signals S3.2-S3.5 are all absent (`pass`) produces no finding, with the log reason `no_signals`; S3.1 and S3.6 alone describe almost every Polish page and are not evidence of advice. An M1 document always yields a finding, because the firm mention (S1.1) is itself the point of M1. Alternative: emit an M3 finding for every unmatched third-party document, capped at 0.4. Rejected because every educational post (mock `8721cb75…`) would land in the analysts' queue. The mocks show `8721cb75…` as an M1 finding with no firm; under plan §2 an unmatched document is never M1, so this change follows the plan and the mock is not reproduced (Open Question 1).

2. **Link hosts count as a registry match for third-party content.** `Registry.match(text, url)` is unchanged for M2. For `third_party`/`unknown`, when the text and page host match nothing, the hosts of `links[].href` are compared with firm domains (same subdomain rule as the page host), with confidence 0.9 and the matching href as the quote. A finfluencer post that links to `eurotrade-markets.example.com/…?ref=…` advertises that firm even if the caption never names it. The page host of a social platform (`instagram.com`) never matches a firm. A malformed href is skipped. A fuzzy-only match still routes to M1, but S1.1 is then `uncertain` (no quote), which addresses skeleton follow-up #11 for M1.

3. **Signal results: `fail` means the signal is present.** This follows the mocks (`S1.3 #współpraca` is `fail`, its absence is `pass`) and the dashboard reading that red marks a risk indicator. `pass` means absent, `uncertain` means a rule found a candidate that only the LLM can confirm, and `not_applicable` means the inputs to judge it are missing (for example S1.6 when the document has neither an author nor a usable page host). S1.5 has no rule part: without a verdict it is `uncertain` with null evidence and the explanation "wymaga modelu językowego". This follows the `analytics-llm-p0` seam, where every implemented rule returns a full rules-only result that the LLM may replace (its design §1-2). Omitting S1.5 instead was rejected because that engine asks the LLM only about results that exist. Whether a disclosed partnership (S1.3 present) should raise or lower the M1 score is a product rule (Open Question 2); the starting weight is positive, as in the mocks.

4. **The shared engine, with M1/M3 catalogues.** Signals are `engine.Rule` subclasses registered with `@register`, and they run through `engine.run_rules`, as `analytics-llm-p0` asks (its design §2). `rules/m1_signals.yaml` and `rules/m3_signals.yaml` use the M2 entry format plus an entry `weight` (number) and a root `bias` (number), read only for M1/M3. The loader takes the module: ids must be `R…` for M2, `S1.<n>` for M1 and `S3.<n>` for M3. The signal parameter keys (design decision 11) are added to `KNOWN_PARAMS`, so typos still fail at load. Names come from `generate_mocks.py`, so output and mocks agree. A separate signal engine with its own judge protocol was the first draft of this design. It was dropped once the sibling published its seam, because two protocols would need two merge paths and two sets of tests. The cost is that both stage-2 branches edit `rules/engine.py` (the loader's id check and `KNOWN_PARAMS`); the edits are small and additive, and the second branch to land rebases them.

5. **Evidence may quote a named document field, not only the text.** Several signals are about metadata: the author handle (S1.6, S3.1), a link href (S1.1 by link, S1.2), the page URL (S3.6 `.pl`, S1.6 by host). `Rule` gains `evidence_fields(ctx) -> list[str]`, which returns `[doc.text]` by default. M1/M3 signal classes that quote metadata override it to also return `author.name`, `author.handle`, each `links[].href` and `url`. The engine's safety net then checks that the quote is a verbatim substring of one of those fields of this document; otherwise the result becomes `uncertain` with null evidence (the `analytics/CLAUDE.md` rule). This is a one-line change in `run_rules`. The explanation says where a metadata quote was found ("w linku", "autor", "adres strony"). The contract `evidence` stays a plain string, so nothing in the contract changes. LLM verdicts are verified against `text` only, by the judge (`analytics-llm-p0`). Alternative: put metadata evidence into `explanation` and leave `evidence` null. Rejected because the dashboard shows `evidence` as the proof, and the mocks already quote `@inwestor_jan` and `register?ref=JAN500`.

6. **LLM seam: the `analytics-llm-p0` one.** `analytics-llm-p0` owns the `LlmJudge` protocol, `SemanticCheck`, `LlmVerdict` and `JudgeOutcome` in `llm/judge.py`, the YAML `llm: {question, when}` block, the one-call-per-module `run_rules(catalogue, ctx, judge=None, module=…, module_context=…)`, quote verification, chunking, cache, breaker and the `judge` parameter of `analyze` (its design §1-2 and the `llm-analysis` spec). This change owns which signals carry an `llm:` block, their Polish questions, the module contexts (`M1_CONTEXT` from plan §4, `M3_CONTEXT` with the Art. 76 definition from annex 3) and the rules-only fallbacks:
   - No `llm:` block (S1.1, S1.2, S1.3, S1.6, S3.1, S3.2, S3.5, S3.6): rules only; the engine never asks about them, so a deterministic `fail` cannot be overruled.
   - S1.4, `when: always`, with an `ask_llm` override that asks only when the rules result is `pass`: a verified LLM `fail` can add an implicit call to action, but a dictionary hit stays `fail`.
   - S1.5, S3.3, S3.4, `when: always`: rules-only, S1.5 is `uncertain` with null evidence; S3.3/S3.4 are `uncertain` quoting the rule candidate, or `pass` with no candidate. A verified verdict replaces the result (`hybrid` when the rule had evidence, else `llm`).
   - No judge, or a judge with no verdict (down, breaker open, budget, invalid output): the rules-only results stand and `model.llm = null`. `model.llm` is set from `JudgeOutcome.model` the same way M2 sets it under `analytics-llm-p0`.
   Landing order: the rules-only groups (1-5) need nothing from `analytics-llm-p0`; before it lands, `llm:` blocks in the M1/M3 YAML are ignored by the skeleton loader (it reads only known entry keys), and `analyze` has no `judge`. Task group 6, which wires the judge into M1/M3 and tests the seam with the sibling's `FakeJudge`, starts only after `analytics-llm-p0` is merged. If that change is late, groups 1-5 still give rules-only M1/M3 for Integration #2.

7. **Score.** `score = σ(bias + Σ wᵢ·xᵢ)` with `x = 1` for `fail`, `0.5` for `uncertain`, `0` otherwise (pass, not applicable), rounded to 3 decimals. Starting values, tuned so the mock scenarios hold rules-only and to be recalibrated on the gold set: M1 bias −3.5, S1.1 0.5, S1.2 2.5, S1.3 1.0, S1.4 1.0, S1.5 2.0, S1.6 1.0. M3 bias −3.0, S3.1 0.5, S3.2 1.0, S3.3 2.0, S3.4 2.5, S3.5 1.0, S3.6 0.5. Worked rules-only results (S1.5 `uncertain` adds 1.0 to every M1 sum): `3c41441c…` M1 ≈ 0.92; `182e5a42…` M1 = 0.50 (≈ 0.73 once S1.5 is confirmed `fail`, ≈ 0.27 if judged educational); `007bbcee…` M3 ≈ 0.90; `cdbf5306…` M3 ≈ 0.56 (≈ 0.82 once S3.4 is confirmed); `72acbb3b…` M3 ≈ 0.27. Tests assert the scenario orderings and threshold sides, not these exact numbers, so retuning the YAML does not break them.

8. **M3 hard gate.** When neither S3.3 nor S3.4 is `fail` or `uncertain`, the M3 score is `min(score, 0.4)` and the summary says so. Counting `uncertain` as present keeps rules-only M3 able to reach the threshold on a page like `007bbcee…`; otherwise no M3 finding could ever raise `finding.high_risk` without the LLM. This is a product rule to confirm (Open Question 3).

9. **Advertiser.** `name` is `author.name`, else `author.handle`, else the page host. `handle` and `profile_url` come from `author`. `website` is `scheme://host/` of the page URL when the document has no author (a web page speaking for itself). A `profile_url` that is not an absolute http(s) URL becomes `null` instead of failing the finding. Strings are trimmed and cut to 200 characters (worker follow-up #8). `in_registry` is true when the author's profile host, the page host (if not a social platform) or the normalized handle (lowercase, `@` and non-alphanumerics removed) belongs to a registry firm, else false. `on_warning_list` is `null` while S3.7 is not implemented. M1 findings carry `firm` from the match; M3 findings carry `firm: null`.

10. **Texts.** Titles and summaries are Polish and built from the results only. M1: `"{advertiser} reklamuje {firm}"` plus the strongest present signal names. M3: `"Podmiot spoza rejestru {advertiser}: …"`. The summary lists present and `uncertain` signals, names S1.5 as not checked when it has no verdict, says when the score was capped by the gate, and says "tryb regułowy (bez modelu językowego)" when `model.llm` is null. `content_excerpt` follows M2 (normalized text, at most 500 characters).

11. **Signal dictionaries (starting set, in YAML).** S1.2: link query keys `ref`, `aff`, `affiliate`, `partner`, `promo`, `coupon`, `referral` and text phrases `kod polecający`, `kod promocyjny`, `z moim linkiem`, `z kodem`; `utm_` alone gives `uncertain` (tracking, not proof of payment). S1.3: `#reklama`, `#ad`, `#współpraca`, `#sponsored`, `współpraca reklamowa`, `płatna współpraca`, `materiał sponsorowany`, `sponsorowany`, `partner`, plus a link with `rel` containing `sponsored`, with R2's same-line negation rule. S1.4: imperative forms such as `otwórz konto`, `załóż konto`, `zarejestruj się`, `odbierz bonus`, `link w bio`, `kliknij`, `dołącz`, `skorzystaj z kodu`. S3.2: `family office`, `wealth management`, `doradztwo inwestycyjne`, `doradca inwestycyjny`, `zarządzanie portfelem`, `indywidualna strategia`. S3.3 candidates: `dopasujemy … do Twojej sytuacji`, `konsultacja 1:1`, `ankieta`/`profil inwestycyjny`, `indywidualnie dobierzemy`. S3.4 candidates: a buy/sell/hold verb (`kup`, `kupno`, `sprzedaj`, `sprzedaż`, `trzymaj`, `rekomendujemy`, `polecam kupić`, `co kupić`) within ±1 sentence of an instrument noun from Art. 2-3 of the Act (`akcje`, `obligacje`, `ETF`, `CFD`, `opcje`, `kontrakty terminowe`, `certyfikaty`, `jednostki funduszy`), negated hits excluded (`nie udzielamy rekomendacji`). S3.5: `abonament`, `subskrypcja`, `sygnały premium`, `VIP`, `płatna grupa`, a price per month (`\d+ ?(zł|PLN) ?/ ?mies`, `miesięcznie`). S3.6: `zł`/`PLN` amounts, `+48` numbers, a `.pl` page host, else the `pl` language guess with null evidence.

No ADR: these choices are local to `analytics/`, follow the accepted plan and ADRs 0301, 0304 and 0305, and are reversible by editing YAML or one module. ADR 0308 stays unused.

## Risks / Trade-offs

- [Rules-only M3 cannot tell education from advice on hard cases] → the gate caps pages without S3.3/S3.4 candidates; candidates are `uncertain`, so the dashboard shows "do weryfikacji"; the LLM refines them when `analytics-llm-p0` lands.
- [Short dictionary words (`VIP`, `partner`, `dołącz`) cause false signals] → word-boundary regexes, negative test cases per signal, and each signal's weight is small compared with S1.2 and S3.4.
- [Metadata evidence weakens the "quote from the text" rule] → the quote must still be a verbatim substring of a named field of the same document, and LLM verdicts are checked against `text` only.
- [Hand-tuned weights drift from real data] → weights live in YAML; tests assert orderings and threshold sides; calibration is plan §8.
- [Seam drift: `analytics-llm-p0` changes its interface before freezing it (its task group 8)] → this change uses only the YAML `llm:` block, `Rule.ask_llm` and the `judge` keyword; group 6 starts after that change is merged and re-reads `llm/judge.py` first.
- [Both stage-2 branches edit `rules/engine.py` and `pipeline.py`] → the edits are additive (an id check per module, new `KNOWN_PARAMS` keys, `evidence_fields`, M1/M3 dispatch); the second branch to land rebases them, and the spec merge order is noted in both designs.
- [Routing change moves a document between modules on re-scan (a firm added to the registry turns an M3 document into M1)] → the worker upserts per `(document_id, module)`, so the old M3 finding stays as it was; acceptable for the hackathon and noted for analysts.

## Migration Plan

Pure code change in `analytics/`; no table, contract or event change. Rollback is reverting the branch: `third_party`/`unknown` documents go back to `module_not_implemented`. Findings already stored stay valid v1 rows.

## Open Questions

Product rules for Damian (not guessed; the starting choice is in brackets and marked in the specs so it is easy to change):

1. Unmatched third-party documents with no advisory signal (mock `8721cb75…`): no finding, an M1 finding with `firm: null`, or a capped M3 finding? [no finding, reason `no_signals`]
2. Does a disclosed partnership (S1.3 present) raise the M1 score (evidence of advertising) or lower it (a missing label is the worse case, also R2)? [raises, weight 1.0, as in the mocks]
3. Does an `uncertain` S3.3/S3.4 (rule candidate, no LLM) lift the M3 hard gate? [yes]
4. Should a `firm_own` document without a registry match also go to M3 (skeleton open question)? [no, M2 only]
5. A `third_party` document whose author is the firm itself (S1.6 `pass`): keep it as M1, or treat it as M2? [M1, scored lower]
6. Do crypto-assets count as instruments for S3.4 (they fall under MiCA, not Art. 2 of the Act)? [no]
7. Should a document that matches a firm and also shows advisory signals produce both M1 and M3 findings (plan §2 "possibly several")? [M1 only]
