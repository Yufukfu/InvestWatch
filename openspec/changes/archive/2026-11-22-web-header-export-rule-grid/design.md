# Design

## Decisions

1. **The header reads the findings filters from the URL.** A container `ReportExport` (in `features/findings/`, rendered by `App` like the other feature pages) uses a data hook `useReportExport(onFindingsPage)`: `useUrlSearch` (re-renders on `popstate` and our own pushes) and `parseFilters`. On the findings page it subscribes to `useGetFindingsQuery(toQueryArg(filters))` with the same arguments as the list, so RTK Query shares the cached request (no second fetch) and the header knows the total. Elsewhere the query is skipped and the filters are the defaults, so the export is everything, and the note says so. Alternative: lift the findings state into `App`. Rejected: it couples every page to the findings hook for one link.
2. **Phone header**: the export lives in its own `.header-export` block after the status badges; below 600 px it is hidden until the `☰` button opens the menu (the same `menuOpen` state as the section links), and the button's `aria-controls` names both regions.
3. **Rule grid squares are buttons** with no action besides focus: a focusable, named control is the simplest way to get the legal basis on keyboard focus without a `tabindex` on a non-interactive element. The tooltip is a sibling `role="tooltip"` element shown by CSS on `:hover` of the cell and `:focus-visible` of the button; the accessible name already carries the legal basis, so no `aria-describedby` repeats it. Rule ids and legal bases come from the API: rendered as text with `dir="auto"`, and isolated (`isolate()`) inside the `aria-label`.
4. **Colours**: `--risk-high` (Naruszenie), `--amber` (Niepewne), `--green` (Zgodne) with white text, `--tint-neutral` with `--text-2` (Nie dotyczy), as in the mockup; the rule id in every square and the legend's words and counts carry the meaning without colour.
